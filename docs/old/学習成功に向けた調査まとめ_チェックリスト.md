## 1. FSRタッチセンサー Z座標ミスアライメント【修正・検証済み】

`assets/humanoid/humanoid.xml`のFSRサイト8点が、ソール底面より3.4cm下（床下空間）にあり、接触を検知できなかった。X,Y座標（`RobotConfig.FSR_POSITIONS`契約）は維持したまま、Z座標とサイズのみ修正。

**波及していた範囲**（今回すべて同じ修正で解決済み）:
- `both_feet_contact`報酬（weight 8.0）が学習全体で常に0
- `foot_balance`（`stability_index`の一部、`com_stab`報酬 weight 10.0に混入）が常に定数0.6667
- `compute_zmp_margin()`内の片脚/両脚支持判定が常に「両脚支持」固定
- `r_cp`（capture point報酬）内のswing/stance脚判定が常に同じ脚に固定

**検証**: 純MuJoCo・実MJXパイプライン双方で`both_feet_contact`が0→1に反転、pytest全38件PASS。

## 2. Reward Audit「Potential Decay」誤検知【修正・検証済み】

`_audit_reward_metrics()`がepisode累積値をそのまま比較しており、`episode_alive`が伸びるだけで誤検知していた。1step正規化＋割引理論値からの乖離判定に変更。

実ログ再監査で151件→0件（Exploitation/Metric Corruption/Action Distortionは元々別途修正済みだったことも判明、Potential Decayのみ今回対応）。異常注入テストでも検出力維持を確認。

## 3. 外乱カリキュラムがeval上で構造的に検証不能【評価パス追加・機構は検証済み】

### 発見した問題
Braxの`Evaluator.generate_eval_unroll()`は評価のたびに`eval_env.reset()`し、`training_progress`を0に戻す（Brax標準仕様、`brax==0.14.2`のソースで確認）。評価1エピソードは最大`episode_length`（500）ステップしかないため、`training_progress`は`500/39,062≈1.3%`までしか到達できず、`CURRICULUM_SCHEDULE_FRACTIONS`の最初の閾値（10%）に構造的に届かない。

`version_9`の全19評価地点で`curriculum_scale=0.000`だったのはこれが原因。**学習ロールアウト自体は正しく進捗している可能性が高いが、それをevalログから確認する手段がこれまで存在しなかった。**

### 追加した機能
- `envs/training_wrapper.py`: `TrainingProgressWrapper`に`fixed_progress`引数を追加。指定すると`training_progress`をその値に固定したままreset/step可能に
- `train/train_mjx.py`: `--eval_curriculum_progress`（デフォルト1.0）で、通常evalとは独立した「外乱カリキュラム固定評価」を`policy_params_callback`内で毎チェックポイント実行し、`<run_dir>/disturbed_eval_log.json`に記録
- `--disturbed_num_eval_envs`（デフォルト64）、`--disable_disturbed_eval`（無効化オプション）も追加

### 検証状況
`TrainingProgressWrapper`+`acting.Evaluator`の組み合わせを、実際のPPO学習ループを介さず直接検証：

| `fixed_progress` | `curriculum_scale`(1step換算) | 期待値 |
|---|---|---|
| `None`（従来通り） | 0.000 | `version_9`ログと完全一致 |
| `0.3` | 0.300 | `CURRICULUM_SCHEDULE_FRACTIONS[0.25]=0.30`と一致 |
| `1.0` | 1.000 | `[0.75]=1.00`（最大外乱段階）と一致 |

機構そのものは設計通り動作することを確認済み。**ただし`train_mjx.py`をフルパイプラインで実際にチェックポイントまで完走させる統合テストは、こちらのCPU環境でのJITコンパイル時間の制約により未完了**。WSL/GPU環境で一度、短いステップ数（例: `--steps 50000`程度）でのスモークテストを先に行うことを推奨します。

## 4. `step_penalty`/`no_step_penalty`に重みが未適用【未対応・意図確認待ち】

`envs/mjx_rewards.py`の`soft_penalty`内、他の項は全て`REWARD_WEIGHTS`で重み付け（0.00005〜0.5）されているのに、`step_penalty`（0〜20にclip）と`no_step_penalty`（0または100）だけ実質weight=1.0のまま加算される。

**私の見解**: 「歩行は対象外」を強制する意図的な強いペナルティであれば妥当（定常状態では値が小さくなるので実害は小さい）。ただし他の項と同様に小さい重みを掛けるつもりだった書き忘れの可能性も残る。

**推奨**: 次の本番学習の前に、意図通りか一度確認してください。意図的なら`REWARD_WEIGHTS`にコメントで明記しておくと、次に見た人（未来の自分やCopilot）が同じ疑問を持たずに済みます。

## 5. `r_still`と`r_com_stab`が同じ重みで二重加算【未対応・意図確認待ち】

```python
r_com_stab = exp(-10.0 * 水平速度²)
r_still    = exp(-20.0 * (水平速度² + yaw_rate²))
total_reward += r_still * w['com_stab'] + lambda_phase * (r_com_stab * w['com_stab'])
```

ほぼ同一の「静止性」信号が同じ`w['com_stab']`(10.0)で二重に加算されており、安定時（lambda_phase≈1が多い現Phase）は実質weight≈20相当になっている。gitログでは同一コミットで導入されているため意図的な可能性もある。

**推奨**: これも次の本番学習の前に意図を確認。もし「常時のstillness＋安定時の追加ボーナス」という設計意図なら、`r_com_stab`側に`com_stab`とは別の小さい専用重み（例: `com_stab_bonus: 2.0`など）を割り当てて明示的にした方が、後からチューニングしやすくなると思います。

## 6〜7. 経過観察項目

- **KLスパイク**: 学習開始直後（最初の1回のみ）`kl_mean=10.25`、以降は0.02〜0.05で安定。初回更新特有のアーチファクトの可能性が高く、再発していなければ実害なしと判断してよさそうです
- **`min_std`のクリップ下限張り付き**: 学習後半、`policy_dist_min_std`が下限0.15に固定される一方`max_std`は1.23→2.03と増加。特定関節の探索が早期に収束している可能性があり、次の学習でも同様の傾向が続くか見ておくとよいと思います

   - `disturbed_eval/episode_curriculum_scale`が`--eval_curriculum_progress`通りの値になる
   - reward auditが誤報を出さない
4. **問題なければ本番の10M step学習を実行**
5. 学習中〜後、`version_9`との比較で以下を確認:
   - 学習曲線が序盤で大きく荒れすぎていないか（新しい報酬項への適応過程は許容範囲内か）
